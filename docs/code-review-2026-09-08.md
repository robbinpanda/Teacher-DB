## 首次审查问题（以下 3 项现已修复，行号对应修复前版本）

### 1. [P1] 已结束作业仍可通过接口修改成绩

- 位置：`lib/school-workflow.ts:250–252`，`saveSubmissionScores`。
- 触发：教师在一个页面结束作业后，另一个仍打开的录分页面提交保存；直接调用录分接口也会触发。
- 原因：服务端只验证作答和教师归属，没有校验 `assignments.status`。前端虽禁用了已结束作业的输入和保存按钮，服务端仍接受写入。
- 复现：将作业设为 `closed`，对 `/api/assignments/{id}/scores` 提交 7 分，返回 HTTP 200、`saved: true`、`totalScore: 7`。
- 影响：已结束作业的历史成绩和学情可被修改，与页面“需先重新开放才能修改”的承诺不一致。
- 建议：在录分的同一个即时事务中检查作业处于 `active` 状态，关闭时返回 409；覆盖关闭与保存交错的回归用例。

### 2. [P2] 非法分数会被强制转换成零分并标记为已批改

- 位置：`lib/school-workflow.ts:254–257`；客户端转换位于 `components/AssignmentWorkspace.tsx` 的 `SubmissionEditor.save`。
- 原因：使用 `Number(value)` 后才验证范围。`null`、空字符串、`false` 和空数组均被转换为 0；客户端清空分数输入也会发送 0。
- 复现：分别提交上述四种值，接口均返回 HTTP 200、`totalScore: 0`，并设置批改完成时间。
- 影响：未录入和错误输入被当作真实零分写入成绩，并进入学情统计。
- 建议：前后端明确区分未录入与零分；服务端仅接受有限数值，要求每题完整填写。前端为空时阻止完成批改，或引入草稿保存状态。

### 3. [P2] 单独共享变式题后，防止连续改写的限制失效

- 位置：`app/api/imports/questions/route.ts:155–159`；限制逻辑位于 `app/api/questions/[questionId]/variations/route.ts:115`。
- 触发：只导出 AI 变式题，不同时导出其原题，然后导入共享包。
- 原因：导入仅在当前包内查找父题；找不到时保留 `parent_question_id = null`。生成接口及题库按钮仅通过这个字段判断题目是否已经是变式。
- 复现：共享包声明 `parentExternalId`，但不包含父题；导入返回 201。数据库保留 `variation_kind`，却将 `parent_question_id` 留空且 `needs_human_review = 0`。
- 影响：题目失去父题关联，题库重新出现“生成变式”入口，绕过“避免知识点逐代漂移”的业务限制。
- 建议：单独存储不可因导入或父题删除而丢失的题目来源类型及外部溯源标识；生成接口同时检查来源类型。补充仅导出子题、跨包导入和删除父题用例。

## 部署边界

`lib/server.ts:13–15` 直接信任 `oai-authenticated-user-id`，缺失时回落至 `local-demo`。这是 README 已声明的本地模式边界，不是本次新增回归。新增学生名单和成绩接口也沿用该机制；在可直接访问服务的环境中，未登录请求指定 `local-demo` 可以读取该空间的作业和学生。

因此当前版本适合受控的单教师本地使用。学校联网部署前，应落实可信登录与会话、代理头清洗、教师与班级授权；缺少身份时拒绝访问，而非自动进入共享空间。当前 `next dev` / `next start` 脚本没有显式限定回环监听，建议为本地模式增加明确的监听配置。
